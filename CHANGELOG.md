# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed
- **No more broken pages after a deploy.** The dashboard's service worker now takes over as soon as a new build arrives (`skipWaiting` + `clientsClaim`): a waiting worker kept serving the previous app shell, whose lazy chunks no longer exist, so pages like Agents failed with "Failed to fetch dynamically imported module". The stale-chunk recovery also activates a waiting worker before its one reload.

### Added
- **Ready-made hosted connectors: a curated catalog to install in one step (Printful, Gelato, Printify).** Connectors → Hosted servers → "Ready-made (hosted by Polpo)" (docs/custom-mcp-servers.md, "Ready-made connectors").
  - **Template features of the hosted server model**: typed, non-secret **settings** (`settingsSchema`: string / number / enum / boolean with label, help, required, default, pattern, bounds) set at install and editable later without a new version, used as `{{settings.x}}` (and `ctx.settings` in code tools); variable fallbacks (`{{input.currency ?? settings.currency}}`); server-level default **query** and **scoped defaults** (`scopes.<name>.headers / query`, applied to the tools that list the scope — e.g. Printful's `X-PF-Store-Id: {{settings.store_id}}` on store endpoints); **output shaping** (`response.filters` by the tool's input, local `page` with `{ items, total, offset, limit, next_offset }`, `aggregates` count / unique / min / max / sum / value) and, when a result is still too long, whole list items kept with a count instead of JSON cut mid-item.
  - **Install flow**: settings → secrets (written straight to the vault entry the template names, never echoed: `PUT /mcp-servers/{id}/secrets/{name}`) → which agents the connector grants (explicit; none by default, said in the dialog) → the template's read-only tests → publish 1.0.0 + deploy. A missing secret or a failing test publishes nothing. Installing a newer template **revision** over an installed server makes it the draft with the diff to publish.
  - **Templates** (`src/mcp-servers/templates/<id>/template.ts`, revisioned, maturity flag, vendor instructions per secret, mocked-API tests in CI): **Printful revision 2** (store setting + header, `list_stores`, products filter and paging, `get_product` summary, `find_variant` by color / size, `estimate_order_costs`, free mockups, draft orders with approval), **Gelato** (catalogs, product search and prices, shipping methods, quotes, orders, draft orders with approval), **Printify** (shops, catalog, `find_variant`, shipping, shop products, orders, orders on hold with approval). Gelato and Printify are not yet tested with the live API.
  - **Surfaces**: dashboard (catalog cards with read-only / approval tools, maturity and status — available, installed vX, update available —, install dialog, Settings tab with settings values and write-only secret inputs that a setup link focuses); REST (`GET /mcp-servers/templates[/{t}]`, `POST /mcp-servers/templates/{t}/install`, `PATCH /mcp-servers/{id} { settings }`); MCP (`polpo_mcp_server_templates`, `polpo_mcp_server_install` with a setup link for missing secrets — setup kind `mcp-server` for `polpo_setup_wait` —, `polpo_mcp_server_update { settings }`); Polpo's chat ("install the Printful connector"); SDK (`getMcpServerTemplate`, `installMcpServerTemplate`, `saveMcpServerSecret`; React `useMcpServers().install`, `useMcpServer().saveSecret`).
- **Agent tests: check everything an agent has at its disposal.** A **Tests** tab on the agent page, each check on its own or **Run all**, ✓ / ⚠ / ✗ with details and a fix (docs/agent-tests.md).
  - **Checks**: `engine` (a minimal real request with the agent's engine and auth, reusing the harness connection test, the CLI account status with the owner policy guard for the person testing, or one tiny completion with Polpo's engine; model and latency), `tools` (every `allowedTools` entry, globs too, resolves to a real tool; unknown names flagged; the rest blocked), `connectors` (each usable connector tested as its Test button does; a connector named in `allowedTools` such as `mcp__printful__*` whose access leaves the agent out is a failure with a **one-click grant**), `vault` (entry names only, engine credential references, `env_from_vault` mappings in instructions and skills), `skills` (load with their files, pinned versions exist), `computer` (live status, never started unless **Start and test**; sandbox provider; egress proxy or the remote computer's tailnet), `channels` (routes to the agent, channel running), `versioning` (production, stale draft), and `smoke` (explicit only: a tiny real chat turn that calls `register_outcome`, checked end to end).
  - **Targets**: production, the draft, or a published version before deploying it (the completions API now accepts `agent@draft`).
  - **History**: runs kept per agent with time, actor, target and version (`.polpo/agent-tests/`).
  - **Surfaces**: REST `POST/GET /api/v1/agents/{name}/tests`, `GET …/tests/{id}`, `POST …/tests/fix` (OpenAPI); MCP `polpo_agent_test` (read scope; the smoke run and the fix need `polpo:admin`); Polpo's `agent_test`; SDK `runAgentTests`, `getAgentTests`, `getAgentTest`, `fixAgentTest` and React `useAgentTests`.
- **Hosted MCP servers: Polpo builds and serves its own MCP servers, and each becomes a connector.** A new primitive (docs/custom-mcp-servers.md).
  - **Model** (`.polpo/mcp-servers/<id>/`): name, description, icon, base URL, **allowed domains**, credentials as **vault references** (`{ owner, service, key }` — never a value; reserved `$` owners refused), auth (bearer, header, query, basic, OAuth2 client credentials), limits, tools with model-facing descriptions, input/output JSON Schema, annotations (read-only, destructive), **requires approval** and **public callable** flags.
  - **HTTP tools (declarative)**, executed in Polpo: URL / query / header / JSON body templates (`{{input.x}}`, `{{secrets.NAME}}` only in headers and query), response mapping (JSONPath-ish `pick` + `fields` + truncation), error mapping, pagination hints. Each call: https only, host in the allowlist, public addresses only, the secret read for that call only and only after the destination passed, redirects never followed, timeout, response size cap, retries on 429 / 5xx for idempotent requests with `Retry-After`, the request returned with secrets masked (also URL-encoded and base64).
  - **Code tools**: `handler(input, ctx)` modules (TypeScript types stripped when Node can) in a **bubblewrap worker per server version**, started on demand and stopped when idle: `--unshare-all --clearenv`, read-only `/usr` and its own build folder only (no instance files, no vault, no home), `ctx.fetch` / global `fetch` made by the host against the allowlist, the sandbox allowlist proxy for libraries that honor `HTTP(S)_PROXY`, declared secrets passed per call in memory, V8 heap limit, per-call timeout that kills the process tree, concurrency limit, result size cap. **npm dependencies** installed at publish with `--ignore-scripts`, lockfile recorded, size capped (100 MB default, `limits.depsMaxMb`).
  - **Authoring**: from an API (OpenAPI URL or pasted document / docs → the orchestrator model proposes a curated set of task-oriented tools; invalid tools and literal secrets dropped), from a description (code tools), blank, or the **Printful template** (catalog categories and products, product + variants, variant, shipping rates, mockup task + result, draft order — approval, never confirmed —, order status, orders; bearer token from the vault entry `polpo-infra/printful`, field `token`).
  - **Test**: run one tool (draft, production or a version) and see the masked request, response, timing and errors; destructive / approval tools are a dry run unless `confirm: true`; saved test cases run on publish (warn, or block with `onTestFailure: "block"`), and never run destructive / approval tools.
  - **Versions**: draft → publish (semver, bump suggested: major for removed tools or changed input schemas, minor for added tools or settings, patch for descriptions) → deploy, rollback, deploy history, git-style diffs — the agent versions helpers (`unifiedLineDiff`, `snapshotToYaml`, semver) and the dashboard's diff view are shared.
  - **Connector**: the first publish creates a connector bound to the server (transport `hosted`, served in process with the instance's credentials; "Hosted by Polpo · v1.2.0"); it behaves like any connector (access, per-agent tools, policies, tool search, task tool scope). Its auth and transport can only be changed in the server. **Approval tools** never run for agents or Polpo: the call is queued and becomes an **Approvals** request; approving runs it once in the server process, rejecting closes it (`ApprovalManager.reject` now resolves requests that are about no task).
  - **Exposure**: private (this instance only) or **public** at `POLPO_PUBLIC_URL/mcp/servers/<id>` (Streamable HTTP, stateless; initialize, tools/list with annotations and outputSchema, structured results, resources for MCP Apps widgets): per-IP and global rate limits (30 / 300 per minute by default), request log with caller IP, kill switch, destructive / approval tools neither listed nor callable unless `publicCallable`; private servers answer 404 from outside.
  - **Surfaces**: dashboard (Connectors → **Hosted servers**, **Create server**, editor with Tools, Settings, Test, Versions, Logs); REST (`/api/v1/mcp-servers…`, in the OpenAPI spec); MCP (`polpo_mcp_servers_list`, `polpo_mcp_server_get|create|generate|update|test|publish|deploy|logs|delete`, changes need `polpo:admin`); Polpo's chat (the same tools, "hosted-servers" group); SDK (`getMcpServers`, `createMcpServer`, `generateMcpServer`, `testMcpServerTool`, `publishMcpServer`, `deployMcpServer`, `rollbackMcpServer`… and React `useMcpServers`, `useMcpServer`); event `mcp-server:changed`.
- **Large artifacts (up to 100 MB), uploads, and partial changes — on every surface.** Agents and MCP clients no longer have to emit a whole artifact in one tool call, nor rewrite 400 KB to change a line.
  - **Storage**: contents over `settings.artifacts.inlineBytes` (256 KB) are kept as content-addressed blob files in `.polpo/artifact-blobs/<id>/<sha256>`; the record (database or `.polpo/artifacts/`) keeps the reference, the size and an 8,000-character excerpt for search and previews. Uploads are streamed to disk, never held whole in memory. Records written inline before (up to 1 MB, with their versions) are moved to blobs once at start-up and on their next change, without loss.
  - **Limits** (`settings.artifacts`, defaults): `maxBytes` 100 MB per content, `versions.maxCount` 30 and `versions.maxTotalBytes` 500 MB per artifact (full snapshots, identical contents shared, oldest pruned first, the current content never), `maxEditBytes` 50 MB for in-place changes and reads by part, `maxTotalBytes` 20 GB for the instance (warning from 80%, then 507). `GET /api/v1/artifacts/usage`; `usage` on every artifact; the versions panel shows "N versions, X MB of 500 MB".
  - **Changes, Claude-artifact style** (REST `PATCH /artifacts/:id`, MCP `polpo_artifact_update`, agents' and Polpo's `artifact_update`, SDK `updateArtifact`): `update` (`old_str` → `new_str`, or `updates[]` in sequence; exact then fuzzy matching like the coding `edit` tool, all or nothing, the closest lines on a miss), `rewrite`, `append` / `prepend`, `patch` (JSON Patch, RFC 6902, on the model: workspace JSON, a design's `{ pages }`, a document's `{ tabs }`) and per-kind `ops` (doc tabs; sheets cells, ranges, styles, rows and columns with formulas and charts following, sheets; slides and their elements; design boards, pages and `set_layer`; motion scenes and layers). Results are validated before saving; every change is a version and honours `expectedVersion`.
  - **Reads by part**: `GET /artifacts/:id/read` (`offset`/`limit` bytes, `outline`, `tab`, `slide`/`slides`, `sheet`+`range`, `board`, `page`, `scene`), also in `polpo_artifact_get`, `artifact_get` and the SDK (`readArtifact`); `GET /artifacts/:id/content` streams the file with Range support; `GET /artifacts/:id` omits contents over 10 MB (`contentOmitted`, `excerpt`); `GET /artifacts/:id/versions/:version`.
  - **Uploads**: `POST /artifacts/upload` (raw body or multipart, type detected from name and content), `PUT /artifacts/:id/content` (`expectedVersion`), uploads in parts `POST /artifacts/uploads` (raw parts, `{ base64, append_to, more }` or `{ path }` of a file of the instance) + `POST /artifacts/uploads/:uploadId/finalize`. MCP `polpo_artifact_upload_prepare` (`{ url }`, `{ path }`, base64 parts) + `polpo_artifact_upload_finalize` (create, or replace with `id`); Polpo gets them as `artifact_upload_prepare` / `artifact_upload_finalize` (group "artifact-uploads"). New agent and Polpo tool `artifact_from_file` publishes a file written in the workspace (a sandbox's file is copied out; outside the allowed folders it is refused). The MCP tool descriptions tell models to prefer upload and `update` over full contents above a few KB, and a 413 points to the upload tools.
  - **Dashboard**: Upload button and drag & drop on Artifacts (CSV and XLSX are converted to a Sheets workspace in the browser; Word, PowerPoint and PDF are refused with a hint), **Replace content…** in an artifact's menu, files over 8 MB sent in parts with progress; artifacts over 10 MB open in a light view (size, download, replace, outline, preview read 64 KB at a time) instead of the editors, with a warning over 2 MB; versions kept as blobs load when shown; streamed `old_str`/`new_str` updates preview live.
  - **SDK**: `listArtifacts`, `getArtifact`, `readArtifact`, `artifactContentUrl`, `createArtifact`, `updateArtifact`, `uploadArtifact`, `replaceArtifactContent`, `uploadArtifactPart`, `finalizeArtifactUpload`, `getArtifactUsage`, `getArtifactVersion`, `restoreArtifact`, `duplicateArtifact`, `deleteArtifact`; React `useArtifactUpload()` (parts with progress).
  - JSON requests to `/artifacts` are capped at 32 MB (was 4 MB with a 1 MB content limit). Docs: `docs/artifacts.md` (changes, reads, uploads, storage and limits).
- **Agent versions: draft → publish → deploy, rollback, deploy history.** Every agent's configuration is versioned (docs/agent-versions.md).
  - **Versions** are immutable semver snapshots of everything that configures an agent (role, identity, prompt, model, engine and CLI account, reasoning, tools and per-connector tools, skills — with the skill versions current at publish time —, limits, compaction, learning, drive, voice replies, sandbox, computers, egress…): `AGENT_FIELD_CLASSIFICATION` classifies every `AgentConfig` field as versioned or excluded and a test fails for an unclassified one. Not versioned: name, creation date, mission-scoped (volatile) agents, the Ink package version, and runtime data (memory, chats, tasks and runs, outcomes, learned items, team membership, connector grants, vault values).
  - **Draft and publish**: edits go to the draft, which starts from what is live in production (after a rollback, rolled-back changes never come back silently); a draft left behind by a rollback or deploy is kept but marked stale with a warning (dashboard, REST `versioning.draft.stale`/`warning`, MCP) and must be rebased onto production (`POST /agents/{name}/draft/rebase`, `polpo_agent_draft`) or discarded before it can be published; publishing makes the next version — always above the highest existing one — with a suggested bump (patch: text/prompt/identity; minor: added tools/skills/connectors/settings; major: engine or model change, removed tools/skills/connectors), overridable, with author, timestamp, release note and the per-field diff.
  - **Deploy and rollback**: the `production` pointer (alias `latest`) is what chats, tasks, missions, schedules, channels, MCP and Polpo run; deploying writes the version live; rollback deploys the previous one (repeated rollbacks walk back); every move is in the deploy history (who, when, from → to, note) with a git-style diff (per-field changes, line diffs of long text, a unified diff of the config as YAML). Runs in flight keep their configuration.
  - **Pinning**: `assignTo: "writer@1.2.0"` (or `agentVersion` on `POST /tasks`) for tasks, mission tasks and therefore schedules, `agent: "writer@1.2.0"` for chats; every run records the version it used (`Task.runs[].agentVersion`, shown on the run card).
  - **Storage**: `agent_versions`, `agent_drafts`, `agent_pointers` (generic: keyed by pointer name), `agent_deploys` and `tasks.agent_version` (SQLite 0019, PostgreSQL 0020); `.polpo/agent-versions/<agent>.json` for file storage. Existing agents are migrated to 1.0.0 deployed to production on start (idempotent); changes written live outside the draft (an agent's own settings, skill assignment, Ink, CLI, file edits) are recorded as deployed versions.
  - **Surfaces**: dashboard (header version + "Draft has changes", **Versions** tab with draft diff, publish dialog, versions list/view/diff, deploys with rollback and diffs, unified or split; dashboard edits always go to the draft); REST (`/agents/{name}/versions`, `/versions/{version}`, `/diff`, `/draft`, `/publish`, `/deploy`, `/rollback`, `/deploys`, `/deploys/{id}`; `GET /agents/{name}` returns `versioning`, `?view=draft` the draft); MCP (`polpo_agent_versions`, `polpo_agent_version_get`, `polpo_agent_version_diff`, `polpo_agent_publish`, `polpo_agent_deploy`, `polpo_agent_rollback`, `polpo_agent_deploys`; `polpo_agent_get` and the agent card show the version); Polpo's chat (the same tools, "agent-versions" group); SDK (`getAgentVersions`, `publishAgent`, `deployAgentVersion`, `rollbackAgent`, `getAgentDeploys`… and React `useAgentVersions`, `useAgentDeploys`).
  - **API compatibility**: `PATCH /agents/{name}`, `polpo_agent_update` and Polpo's `update_agent` accept `publish`, `deploy`, `bump`, `version`, `note`; without them the draft is published and deployed at once while `settings.agents.versioning.autoDeployApiUpdates` is true (the default, so existing clients keep the immediate effect). Configuration → General → Agent versions and `polpo_config_update auto_deploy_agent_updates` change it.

### Fixed
- **Bulleted and numbered lists in chat answers are indented again.** Streamdown's list classes (`list-inside`, `[li_&]:pl-6`) were never generated because Tailwind does not scan `node_modules`; `ui/src/index.css` now adds `@source "../node_modules/streamdown/dist/*.js"`, so bullets no longer hang outside the message on the left.

### Added

  - **Polpo's tools** reach the CLI: the harness engine's host tools (connectors with their accounts, `register_outcome`, artifacts, memory, data, messages, vault-granted tools, the task's tool scope, `allowedTools`) served as the run's MCP server with a per-run token — this server's loopback, or `<POLPO_PUBLIC_URL>/api/v1/harness-relay/<token>/mcp` for a remote computer. Claude Code gets `--mcp-config`, `--strict-mcp-config`, `--allowedTools=mcp__polpo` and `ENABLE_TOOL_SEARCH` as the harness sets it; Codex `-c mcp_servers.polpo.*` with the token in `POLPO_MCP_TOKEN`. ### Fixed
- **A failure a re-run cannot fix is no longer reviewed, fixed or retried behind your back.** A run that fails with a non-retryable error (`TaskResult.retryable: false`: the model is not enabled for the account, e.g. Bedrock 403 with quota 0, or the credentials are refused) now fails the task after that one attempt with the labelled message as its error ("Bedrock: model … not enabled for this account — …", "Anthropic: authentication failed — check the credentials …"): the assessment is skipped (no reviewer spend on a run that did nothing), there is no fix loop and no automatic retry, a task with `sideEffects` fails instead of waiting for approval to re-run, and the deadlock resolver no longer retries such a failed dependency (the blocked task fails instead). The `retryable` flag travels in the run's result JSON, so the file, SQLite and PostgreSQL run stores need no migration. Escalation policies still apply, and a manual retry (dashboard, `POST /api/v1/tasks/:id/retry`, MCP `polpo_task_retry`, Polpo's `retry_task`) still works. The task page's Details now say "Not retried: the error is not retryable" next to the retry count, as the MCP tools and cards and Polpo's task tools already did. Spending limits and network or transient errors stay retryable.
- **A stopped command no longer leaves its programs running.** When an agent's `bash` command timed out or the agent was stopped, only the shell was killed: what it had started (`npm run dev` → node, a `sleep` in a pipeline, a server started by a script) kept running on the host and kept the output open, so the tool could hang until they finished. Commands on this machine now run in their own process group and a timeout or an abort stops the whole group: SIGTERM, then SIGKILL after 2.5 s if anything is still alive (Windows: `taskkill /T /F`); the call returns as soon as the shell is gone, even if a program that escaped the group still holds the output. Commands still running when Polpo exits are killed too. One helper (`src/sandbox/process-tree.ts`: `spawnTree`, `killTree`, `runCommand`) serves every path: the local and bubblewrap workspaces and Docker (`run`), `NodeShell` (was execa, which killed the shell alone and waited for the pipes) and the host machine of agent harnesses (`exec` and long-running `spawn`). The `bash` tool now also passes the agent's abort signal (`ShellOptions.signal` in `@polpo-ai/core`), so stopping a task stops its running command. Timeout messages and `(no output)` are unchanged.
- **Computer webhooks: the card's counts and its Events sheet disagreed** (e.g. Daytona "7 ignored, 1 rejected" on the card, 0 everywhere in the sheet). The status file's counters had been counting since before the event log existed, while the sheet counts the log. The counts of `GET /api/v1/computer-webhooks` (`received`, `ignored`, `rejected`, `errors`) now come from the event log, the sheet's source. An older `.polpo/computer-webhooks.json` is migrated on first read, once (now `version: 2`): what its counters held beyond the log's entries moves to a new `before: { received, ignored, rejected, errors, until }` (totals with no detail). The card and the sheet's header show it as a muted line, "Before the event log: 7 ignored, 1 rejected — no details"; so do MCP `polpo_computer_webhooks` and the SDK type (`ComputerWebhookStatus.before`, `ComputerWebhookCountsBefore`).
- **Computer webhooks: "not configured" no longer sticks after the signing secret is saved.** The status kept the last error from before the configuration (`lastError: "Daytona webhooks are not configured on this instance"` next to `state: "configured", secretSet: true`), so Settings → Computers kept saying so. Saving the secret (or registering E2B's endpoint, or removing it) now clears the last error and records when the provider was configured; an accepted delivery clears it too; the status shows only errors from after the configuration and never a "not configured" error once configured (also for status files written by the previous version). A provider configured but silent gets `waitingNote` ("Waiting for the first event": Daytona currently sends webhooks only for its classic sandboxes, not for Daytona v2 VMs), and keeps the 5-minute reconcile: the reconcile slows to 20 minutes only while every provider in use has sent an event in the last 24 h (before: as soon as it was configured).
- **Harness relay: requests with a body no longer fail with 400.** The public relay route passed the incoming `content-length` to the run's socket next to `transfer-encoding: chunked`, which Node rejects; every model call through the relay (API key or gateway auth, OpenCode on Bedrock) failed before reaching the provider. Found by the live OpenCode spike.
- **Security: the `grep` tool ran its pattern through the shell.** The pattern, `include` and path were wrapped in double quotes (`JSON.stringify`) inside a `sh` command line, so a pattern such as `$(touch PWNED)` or one with backticks executed on the agent's machine or computer. User input now never reaches a shell unquoted: on this machine `rg` / `grep` are spawned with an argument list (no shell); through a sandbox or remote VM shell every argument is single-quoted (`src/tools/argv-exec.ts`). Audited the other coding tools: `glob` and `ls` go through the FileSystem (no shell), the remote FileSystem and the browser / PDF tools already single-quote. Tests run the payloads locally and through a real `sh` standing in for a VM shell.

## [0.6.1] — 2026-11-22 — MCP permissions and solid schedulers

### Added
- **Per-area permissions for Polpo's MCP connector.** Eight scopes instead of one: `polpo:read` (always), `polpo:work` (ask Polpo, chat, tasks, missions, artifacts, rooms, memory, schedules, approvals), five areas given one by one — `polpo:files` (write, move, delete files), `polpo:messages` (send on Telegram, WhatsApp, email; channel test), `polpo:connectors`, `polpo:computers`, `polpo:vault` (reads too) — and `polpo:admin` (team, settings, skills, notification rules, learning, the REST fallback; it includes everything). Every tool needs exactly one scope; destructive ones the write scope of their area. The tool → scope matrix is generated from the code into `docs/mcp.md` (`node scripts/generate-mcp-scopes.mjs`; a test keeps it in sync) and served at `GET /api/v1/mcp/access`.
  - **Consent:** the OAuth page lists the scopes in plain words with checkboxes (read always; the ones the client asked for checked, the others offered); the person narrows or adds, and the token carries what was allowed (`scope` in the token response, RFC 6749). A client that asks for nothing gets read and work, not admin. A refresh may ask for fewer scopes, never more. A client allowed with an MCP key gets at most that key's scopes.
  - **Metadata:** `scopes_supported` lists the eight scopes in the protected-resource and authorization-server documents; the first `401` suggests `scope="polpo:read polpo:work"`.
  - **Step-up:** `tools/list` shows only the tools the caller's scopes allow; calling another anyway gets `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="<held + needed>", resource_metadata="…"` and a JSON-RPC error (`-32003`) naming the missing scope, so a client can re-authorize with more.
  - **MCP keys with scopes:** `POLPO_MCP_KEY_SCOPES` (space-separated) narrows `POLPO_MCP_KEY`; named keys in `settings.mcp.keys: [{ name, keyRef: { owner, service }, scopes }]` keep their value in the vault (default read and work) and act as `mcp-key:<name>`.
  - **Settings → MCP access:** the connected apps (client, who allowed it, scopes, connected, last used) with Revoke (`DELETE /api/v1/mcp/grants/:id`), and the keys with their scopes — names only, never values.
  - **Audit:** events caused through MCP carry `scopes` next to `by`, and the server log names them on every MCP message.

### Changed
- **MCP scope changes for clients with narrowed scopes** (none existed before: every token and key held the old `polpo` scope): sending a message and testing a channel need `polpo:messages` (was `polpo:work` / `polpo:admin`); writing and managing files `polpo:files` (was `polpo:work`); connector, computer and vault tools `polpo:connectors`, `polpo:computers`, `polpo:vault` (were `polpo:admin`, which still covers them).

### Deprecated
- **The all-in-one `polpo` scope.** Tokens issued with it and the legacy `POLPO_MCP_KEY` without `POLPO_MCP_KEY_SCOPES` keep every scope, so connected Claude/ChatGPT connectors and live keys work as before; the server warns once about an unnarrowed `POLPO_MCP_KEY`, and the dashboard flags both. New consents never issue `polpo` (a client asking for it is offered every box) and metadata no longer lists it.

### Fixed
- **Schedules: nothing lives only in memory any more.** A paused schedule resumed after a server restart; a run due while the server was down was silently lost (a one-shot vanished); two server processes (or a CLI next to the server) on the same storage could fire the same run twice.
  - A schedule's state — paused or not, next and last run, how the last run went (`lastOutcome`: started, completed, failed, skipped, missed, expired; `lastError`), runs missed while the server was down (`missedRuns`, `lastMissedAt`) and its catch-up policy — is stored in every backend: `.polpo/schedules/` (file), and the new `schedules` table on SQLite and PostgreSQL (migrations `0011_scheduling` / `0012_scheduling`, which also add `leases` and `task_watchers`). A restart keeps a pause and the next run.
  - Runs missed while the server was down follow `catchUp` (per schedule, `POST`/`PATCH /schedules` and `polpo_schedule_create`/`polpo_schedule_update` `catch_up`): `"once"` (default) runs the latest missed one at startup if it is at most one interval late (24 h for a one-shot), counting the others as missed; `"none"` skips to the next run and reports them (`lastOutcome: "missed"`). A run still going when its next time comes is late, not missed. Resuming a paused schedule does not run what came due while it was paused.
  - Every occurrence is claimed before it fires (a lease keyed by schedule and scheduled time: a row in `leases` on SQLite/PostgreSQL, a lock file in `.polpo/leases/` on file storage), and the state with the next run is saved before the mission starts: two processes, or a restart in the middle, never run it twice. A schedule paused, changed or created by another process is picked up within a check.
  - A recurring run that was going when the server restarted goes back to `recurring` when it finishes (it ended as completed/failed before: the scheduler forgot it was recurring), and a mission that fails to start is the run's outcome (`failed` with the error) instead of an unhandled rejection.
  - Status everywhere: `GET /schedules` and the new `GET /schedules/:missionId` add `paused` (a one-shot that ran is done, not paused), `catchUp` and `missedRuns`; `polpo_schedules_list` shows `paused`, `last_outcome`, `last_error`, `missed_runs`, `last_missed_at`, `catch_up`; Polpo's `list_schedules`, `polpo schedule list` and the Schedules page and mission detail show Enabled / Paused / Done, the last outcome and the missed runs.
  - `polpo_mission_wait` no longer says "It runs again on its schedule" for a paused schedule: it says it is paused until resumed (or that a one-shot is done), and gives the next run time otherwise.
- **Task watchers survive a restart.** Watchers ("when task X is done, do Y") were only in memory: they are stored now (`.polpo/watchers/`, `task_watchers` table), loaded at start, and one whose task reached its status while the server was down fires then; with several processes the action runs once.
- **Recurring checks: a time that has passed is refused; one run per occurrence; a vanished chat is reported.** `at` in the past (REST, MCP `polpo_check_create`, Polpo and agent tools) was accepted, stayed active, never ran and left its new chat session behind: it is refused before anything is made. A due run is claimed (lease) so two processes run it once; a run deferred because the session is busy gives the claim back for the next tick, and one cut short by a crash is retried after the claim expires. A check whose chat session was deleted and has no other target ends with `lastError` saying so, instead of staying active.

### Fixed
- **Daytona v2 Linux VMs could not be created**: Linux accepts only "delete" as a lifecycle action, so computers and pooled VMs no longer ask Daytona to pause them (Polpo's idle reaper pauses them), and idle triggers are set explicitly instead of inheriting the project's dashboard defaults.
- **Inactive Daytona snapshots.** Daytona deactivates snapshots nobody used for a while, and every run then failed with "Snapshot … is inactive". - **Daytona network allowlists.** Host names were resolved on the server to IP addresses (CDN addresses change, wildcards only covered the base domain) and sent as up to 50 CIDRs plus 4 DNS resolvers, while Daytona accepts at most 10, so larger allowlists failed at create. E2B: `*.example.com` now also allows `example.com`, as on this machine.
- **Daytona commands lost their stderr:** it came back mixed into stdout and `stderr` was always empty. Commands now return stdout and stderr apart (still one call per command), with the exit code.

New `polpo_egress_status` (read-only, computers toolset): each egress proxy (reachable from the server, agents and host computers using it), agents naming a missing proxy, and each remote computer's egress through Tailscale; backed by the new `GET /egress`.

## [0.5.2] — 2026-11-03 — Fixes from DeltaPolpo, chat attachments and voice notes

Most of these fixes are by @DeltaM128 (#149–#183).

### Security
- **Task agents could read and write the project's `.polpo` folder.** The file tools keep agents out of `.polpo` (configuration, `.env`, vault, sessions, storage mounts), but the guard was only switched on in the server process. Tasks run in a separate runner process, where it was off: an agent with the default access (its working directory) could read `.polpo/.env` or the vault file and write anywhere in `.polpo`. The runner now sets the same guard before building the agent's tools, with the same exceptions (offloaded tool outputs, skills, playbooks). A task output folder that lies inside `.polpo` stays writable: it is now granted explicitly. (#150)

### Fixed
- **Files could not be attached in the chat.** The composer accepts any file (`*/*`), but its check read `*/*` literally and refused every file picked or dropped (pasted images went another way). It now accepts any file, matches extensions, and takes the type from the name when the browser gives none (a Telegram `.ogg` export). The limit is 15 MB, as on the server.
- **Audio attached in the chat is transcribed**, as Telegram voice notes are: its words join the message (`[audio name.ogg, transcribed: "…"]`), so the model reads them now and in later turns. The file stays attached.
- **Telegram: replying to a voice note.** A mention of the bot in reply to someone's voice note, photo or file ("@bot what does it say?") brings that media along, even when the bot never received the original. Telegram includes it in the reply. The same holds for a reply to an earlier voice note in a private chat. The bot's own voice replies are not read again.
- **Telegram: failed polling is logged.** A failed `getUpdates` was ignored, so two programs reading the same bot (`409 Conflict`) lost messages without a trace. It is now logged once every 10 minutes, saying what to do.
- A task whose model call failed (e.g. Ollama answering HTTP 500 because the model crashed while loading, or a connection error) ended as **done** with no output and no work: the agent ends such a run with an error reply instead of throwing, and the engine counted it as a success. It now fails with the reason (`Model error: …`), so it is retried and then shown as failed. (#149)
- A run stopped at the turn limit is not a model error: stopping the agent at `maxTurns` ends its last call with an abort error, so the run ends as a normal one (its expectations decide) and its output says `[Stopped at the turn limit (N turns)]`. (#149)
- Tool calls whose arguments did not match the tool's schema were run or previewed anyway: e.g. a local model putting the mission name inside `data` produced a mission preview without a name. The chat now checks every call against its schema (pi-ai's validator) before running or previewing it; a call that does not match is returned to the model with the reason, so it can call the tool again in the same turn. An object or array parameter passed as a JSON string is still accepted, as before. (#151)
- **A playbook that cannot run says why, and which task to fix.** The reason was shown only in a toast that disappears in seconds, and it named fields by index (`tasks.0.description: task requires a description`). The Run dialog now keeps the reasons on screen until the next try, and they name the task, checkpoint or delay (`task "test" (tasks.0).description: task requires a description`). (#152)
- **The mission graph disappeared when a run paused at a checkpoint** (nodes and connections gone, only the background left). On every status update the graph was rebuilt with new node objects that had lost the size React Flow had measured; React Flow hides a node of unknown size and measures it again only when its size changes. Task cards change size with their status, so they came back, but at a checkpoint nothing changed size and the whole graph stayed hidden. The rebuilt nodes now keep their measured size (mission page). (#153)
- `ui/server.mjs` did not work on Windows: every file, including the JavaScript and CSS in `/assets`, was served as `index.html`, because the path check expected `/` separators, and the default static root was built from a URL path (`/D:/...`). The server now uses the platform's paths and still refuses paths outside the static root. (#154)
- **Line numbers copied from `read` into files.** The read tool shows each line as `<n><TAB><text>`, and agents of every size copied those numbers into what they wrote (with the tab, a space, the escape `\t`, a dot or nothing, sometimes with `\n` written instead of the line breaks), so a file ended up with numbers that were never in it. `write` and `edit` now refuse content whose every line starts with consecutive line numbers, with text after them on most lines (a file of numbers, one per line, is data), with an error that says why; `keep_line_numbers: true` lets a file whose lines really are numbered through. An `edit` whose `old_text` carries the numbers says so instead of a bare "not found", and the read tool's description says the numbers are not part of the file. (#161)
- **The glob tool found nothing for patterns with a folder** (`docs/report.md`, `src/**/*.ts`), and nothing at all on Windows without bash: it ran `find -name`, which matches file names only, through a Unix shell. It now walks the files itself (`src/tools/glob-files.ts`, on the FileSystem port, so remote sandboxes too), with `*`, `**`, `?`, `{a,b}` and `[abc]`; `node_modules` and `.git` are walked only when the pattern names them. (#161)
- **The bash tool failed for every command on Windows** ("uv_spawn '/bin/bash' ENOENT"): the local workspace always ran `/bin/bash -c <command>`. On Windows it now uses Git for Windows' bash (from the usual install folders, or next to `git` on PATH; never `System32\bash.exe`, the WSL launcher), else `cmd.exe`; `POLPO_SHELL` picks another bash-compatible shell. Commands no longer open a console window. Linux and macOS are unchanged. (#162)
- **A context-full error from Ollama or llama.cpp was not recognized** ("request (16384 tokens) exceeds the available context size"), so the task failed instead of compacting its conversation and retrying once, as it does for the other providers' overflow errors. (#163)
- **A mission or playbook task's `maxRetries` was ignored:** every task got the project's `settings.maxRetries` (3 by default), so a task meant to fail at once (`maxRetries: 0`) was retried three times. The task now keeps its own value; `POST /tasks` accepts `maxRetries` too. (#164)

CORS now runs first (preflight requests no longer count against the limit) and `Retry-After` is exposed. (#166)
- **A runner that could not start ended the whole server** (for example a project folder longer than Windows' 260 characters, or one that no longer exists): the start error came as an event nobody listened to. The task now fails with the reason and the working folder, and the server keeps running. (#167)
- **A `dependsOn` on a task listed after it was dropped in silence**, so the task started at once, in parallel with the one it should have waited for: the tasks were created in the listed order, and a dependency not yet created had no id to point to. They are now created dependencies first (the listed order is kept otherwise, and the output folders keep their numbers). A `dependsOn` naming a task that does not exist, or a cycle (`A` → `B` → `A`, which would never start), is now refused with a message that names the task; renaming a task in a mission keeps the `dependsOn`, checkpoints, delays and quality gates that point to it. (#169)
- **An agent limited to some tools was told it had all the core ones**: the agent's prompt listed read, write, edit, bash, glob, grep, ls, http_fetch, http_download, register_outcome and the vault tools as "always available", and the Ink tools too, whatever its `allowedTools`. An agent limited to the file tools tried `bash` ("Tool bash not found") or wrote that it had run a command it never could. The prompt now names only the tools the agent gets, with the same filter that creates them (the vault tools come with every agent); an agent without `bash` is told it has no shell and not to claim tools it does not have, and the bash rules are left out of its task message. (#170)
- **On Windows, `file_exists` expectations on an absolute path always failed** (`C:\data\x.csv`, `C:/data/x.csv`, `\\server\share\x.csv`): the check read a Windows absolute path as relative to the working directory and looked for it there. (#177)
- **On Windows, `test` and `script` expectations and metrics ran in `cmd.exe`**, while the agents' commands run in Git's bash: a check written for bash (`test -f …`, `grep -q …`) always failed there. They now run in the same bash (cmd.exe only when Git's bash is missing); Linux and macOS are unchanged. (#178)
- **On Windows, a command stopped for its timeout kept running** (the bash tool, checks): only the shell was ended, and the program it had started went on, keeping the run waiting until it finished by itself. Now the msys process groups of Git's bash are ended (the programs it runs are linked to it there, not in the Windows process tree, so `taskkill /T` alone misses them), then the Windows tree; a stopped command no longer waits for its output to close. ## [0.5.0] — 2026-10-25 — Artifacts and the MCP connector

### Added
- **Artifacts** replace Views: one concept for what agents and people make to look at and keep.
  - **Types:**
    - `doc` (Markdown);
    - `html`, one self-contained page with a kind: dashboard, design, app, report, page;
    - `svg` (a drawing) and `mermaid` (a diagram);
    - `view`, the former data views, still shown and working.
  - **Data in html artifacts:** the page runs isolated, in a sandbox without same-origin and with a strict CSP: no network except a few CDNs for libraries. It reads the instance's data sources through a `polpo` bridge with the **rights of its author**: an agent's artifact sees only the sources and fields that agent is granted. The bridge offers:
    - `polpo.sources()`, `polpo.describe(id)`, `polpo.query({...})` and `polpo.sql(id, …)` (read-only);
    - `polpo.onRefresh(fn)`, called every `refreshSeconds` and when a data source changes;
    - `polpo.theme` / `polpo.onTheme`.
  - **Versions:** every change keeps the previous content with its author and note, and any version can be restored.
  - **Tools:** `artifact_create`, `artifact_update` (whole content, or find/replace edits), `artifact_get` (also earlier versions), `artifact_list`, `artifact_delete`.
    - Polpo has all of them; agents get them with `artifact_*` in allowedTools (a new "Artifacts" category in the Tools tab).
    - Agents change only their own artifacts.
    - `navigate_to` gains `artifacts` / `artifact`.
  - **API:** `GET/POST /artifacts`, `GET/PATCH/DELETE /artifacts/:id`, `POST /artifacts/:id/restore/:version`, `POST /artifacts/:id/data` (the bridge). The event is `artifact:changed`. Storage is the `artifacts` table (SQLite/Postgres migrations) or `.polpo/artifacts/` in file mode.
  - **UI:**
    - an **Artifacts** section (replacing Views in every menu) with a gallery by type and search;
    - a viewer with live content, versions and restore, source, data reload, full screen and download;
    - in the chat, a card for each artifact made or changed, which opens it next to the conversation.

- **Polpo as an MCP connector:** every server is also an MCP server at `/mcp` (Streamable HTTP, stateless), so Claude Code, Codex, Claude Desktop, Cursor and other MCP clients can use the instance.
  - **Tools:** 22 tools for what people do (`ask_polpo` delegates anything to Polpo; `chat_with_agent`; tasks, missions, artifacts, data, approvals; files: `list_files`, `search_files`, `read_file` with text by line ranges and images and PDFs as they are, `write_file`, `manage_file` to make folders, rename and delete) plus `list_operations` / `call_operation`, which reach every REST operation of the server (more than 300). There is not one tool per endpoint, to keep the model's context small. Read-only and destructive tools (`call_operation`, `resolve_approval`, `write_file`, `manage_file`) are annotated.
  - **Authentication:** the API key as `Authorization: Bearer` or `X-API-Key`, or **OAuth 2.1**, so it can be added as a custom connector in Claude (web, Desktop, mobile) and ChatGPT.
    - **Discovery:** a `401` with the protected-resource pointer, then RFC 9728 and RFC 8414 metadata.
    - **Client registration:** Client ID Metadata Documents or Dynamic Client Registration.
    - **Codes:** authorization code with PKCE S256 only, `iss` in the response, loopback redirects on any port for Claude Code.
    - **Consent page:** signed in to the dashboard, or with the API key or MCP key; it has a session-bound CSRF token.
    - **Tokens:** 1-hour access tokens and 30-day refresh tokens rotated at every use, stored hashed in `.polpo/oauth.json`; `/oauth/revoke`.
    - **Public URL:** the `X-Forwarded-*` headers when behind a proxy, or `POLPO_PUBLIC_URL`, which may carry a path (a proxy that mounts Polpo under `/name`) and applies to requests through its host.
  - **Publishing only the connector:** `POLPO_MCP_KEY` opens `/mcp` and the consent page without putting an API key on the dashboard and REST API, so an instance can expose `/mcp`, `/oauth` and the discovery documents (for example with Tailscale Funnel) and keep the rest private. Since these endpoints can be public, open client registration is capped (200 clients; ones holding tokens are kept), and client metadata documents are fetched only from public addresses.
  - **Same rules:** the tools call the server's own REST API in process.
  - **stdio:** `polpo mcp --url <server> --api-key <key>` runs the same tools over stdio for clients that start a process.
  - **Setup guide:** `docs/mcp.md`.
- The API key middleware also accepts `Authorization: Bearer <key>`, not only `X-API-Key`.

### Changed
- Polpo's prompt now says when to make an artifact (documents, dashboards on real data, designs, diagrams) and keeps `render_widget` for small throwaway visuals in the chat. The old prompts contradicted each other on views vs widgets.
- `data_create_view` / `data_update_view` are deprecated in favor of html dashboards. `/views` redirects to the artifacts of type view.

## [0.4.8] — 2026-10-13 — Drive

### Added
- **Agent drive** (`drive` in the agent config, off by default): an agent pursues a purpose and goals on its own initiative, among people, instead of only answering when called or scheduled.

It decides by itself whether to write now (`send_message`), plan something for later, or do nothing, weighing how much it serves its purpose, how serious and how urgent it is.
  - **Intentions:** while it talks or reflects, it plans follow-ups on its own, such as wishes on someone's birthday or a check-in after an event. An intention is a scheduled check with a `why`.
  - **Autonomy:** with `propose`, its own initiatives wait for a yes; with `balanced` (the default), it acts on low-stakes things and asks first otherwise; with `act`, it uses its own judgment. Proposed checks are approved with `confirm_check`, by Polpo, or in the UI.
  - **Self-portrait:** it keeps a self-portrait covering its personality, the people who matter and its open threads, updated with `update_self` and part of every conversation. It starts from the identity's personality, or writes one coherent with its purpose.
  - **Human customs:** its prompt covers birthdays and holidays, tact in groups vs private, choosing the moment, not nagging, and stopping when asked.
  - **Goals in a cascade:** it breaks its purpose down into long-term (6–12 months), quarter, month, week and day goals, each under the one it serves, with a measure, progress, an owner (its own, or a person's or group's it supports) and the steps to do. It keeps them in its plan with `add_plan_item` / `update_plan_item`, and the plan is part of every chat.
  - **Review rhythm:** when its day starts (`dayStartsAt`, default 07:30 in its timezone) it plans the day. On a new week, month or quarter it also does that review: score, adjust, set the next goals, and check in with the people it supports.
  - **Method:** the guidance follows goal-setting research:
    - specific, measurable goals, at most 3–5 per horizon;
    - if-then plans for key actions;
    - important before urgent, with timeboxed work sessions;
    - progress monitoring;
    - autonomy-supportive help for people's goals (ask, offer options, never shame);
    - for groups, shared goals with regular check-ins.
  - **Growing:** it asks what it could do more or better and what it lacks, studies it with its tools, and writes its own skills. With a drive it always has its own-skill tools (`list_my_skills`, `create_my_skill`, `update_my_skill`), which can be undone in the Learning tab.
  - **Polpo:** `add_agent` / `update_agent` take `drive`; `get_agent_drive` shows the purpose, self-portrait, intentions and reflections; `reflect_agent` makes the agent reflect now.
  - **API:** `GET /drive/:agent`, `PUT /drive/:agent/self`, `POST /drive/:agent/reflect`, `POST /drive/:agent/intentions/:id/confirm|cancel`; the event is `agent:reflected`.
  - **UI:** a **Goals** tab in the agent page with purpose, goals, autonomy, day start, self-portrait (editable), the goals and steps tree (mark done or drop), planned and proposed intentions (approve or reject), and the reflections journal.
  - **API:** `PATCH /drive/:agent/plan/:id`.
- Scheduled checks gained a `proposed` state (waiting for a yes) and a `why`.

### Fixed
- **Desktop app:** no task ever ran. The compiled server started task runners with a script path that does not exist inside the binary ("too many arguments. Expected 0 arguments but got 3"); it now starts them with a hidden `__runner` command.
